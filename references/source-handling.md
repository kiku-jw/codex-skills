# Source Handling

Choose the lightest inspection path that gives a trustworthy read.

## Articles and websites

- Prefer the original article, docs page, pricing page, or release note.
- Check publish or update dates when the claim could be stale.
- If the finding is a social summary of an article, trust the article, not the summary.

## GitHub repos

- Check the README, license, language mix, archived status, and recent release or tag surface when relevant.
- If the post claims a license, language, or feature, verify those specifically.
- Name clearly if the value is a reusable pattern rather than a reusable tool.

## Screenshots and images

- Describe what is visible before inferring.
- Separate visible text from interpretation.
- If the screenshot is ambiguous, say what cannot be verified from the image alone.

## Videos

Inspect in this order:

1. title and description
2. chapters and linked resources
3. transcript if it can be extracted cheaply
4. supporting pages or posts about the same video

- If you only have metadata, say so.
- Do not pretend to know the full argument from the thumbnail and title alone.

## Social posts

- Separate the actual idea from the performative framing around it.
- If the post links to a deeper source, inspect that source.
- Treat claims in the post as unverified until checked.

## Multiple findings

- Process items tied to active work first.
- Then process items that match the user's recurring themes.
- Leave generic curiosity bait for last.

## Duplicate checks

When the finding is a skill, tool, plugin, or repo that might already exist locally:

- check `~/.codex/skills/` for installed skills
- check the current workspace and nearby repos for the same project or equivalent tool
- check obvious installed commands only when that verification is cheap

If the duplicate check is partial, say so.
